# Python 开发约束

本约束为强制规则，不是建议。任何与以下条目冲突的实现都必须调整。若某条规则在当前任务中确实无法满足, 必须暂停并说明原因, 等待确认后再继续。

## 1. 中文注释标点规范

所有中文注释、docstring 中的标点一律使用**半角符号, 且标点后紧跟一个空格**。

- 正确: `# 计算用户总数, 并按 ID 排序`
- 错误: `# 计算用户总数，并按 ID 排序` (全角逗号)
- 错误: `# 计算用户总数,并按 ID 排序` (缺空格)

标点映射规则:

| 全角 | 半角 | 示例 |
|---|---|---|
| ， | `, ` | `先校验, 再写入` |
| 。 | `. ` 或句末省略 | `该分支不可达.` |
| ： | `: ` | `注意: 此处有副作用` |
| ； | `; ` | `失败重试 3 次; 超时 5 秒` |
| ？ | `? ` | `是否需要缓存?` |
| ！ | `! ` | `禁止传入 None!` |
| （） | `()` | `调用前需初始化 (见 setup)` |

括号内侧不加空格, 外侧按语义正常加空格。不使用全角引号, 需要强调时直接用半角双引号或省略。

适用于 `#` 行注释、docstring、以及所有会被人类阅读的中文说明文本。

## 2. 最小函数化原则

**禁止为一次性逻辑新增函数。**

判断标准:

- 逻辑只被调用一次, 且函数体 ≤ 3 行 → 必须内联, 不得抽取为函数
- 逻辑被调用 ≥ 2 次 → 允许抽取
- 不得为了「结构清晰」「看起来整洁」而创建辅助函数、wrapper、私有方法
- 修改现有代码时, 优先把已有的一次性函数内联回调用处, 而不是新增包装函数

例外情况 (可以定义函数):

- 需要被单元测试覆盖的核心业务逻辑
- 递归实现
- 装饰器、回调、生成器
- 需要资源管理且会显著降低主流程可读性

核心原则: **代码量优先于抽象层级**。宁可写 5 行直白的顺序代码, 也不要拆成 3 个各 2 行的函数。

## 3. 大功能的面向对象边界

自成一体的超大功能 (模型训练、微调、推理、数据管线、完整业务流程) 使用类来承载共享状态, 但类的规模必须受控。

### 何时用类

**同时**满足以下条件时, 才使用类:

- 功能自成一个单元, 代码量超过约 150 行
- 存在跨多个阶段的**可变共享状态** (模型、优化器、tokenizer、device、epoch 计数、缓存)
- 该状态需要在 3 个以上阶段间流转 (如 setup → train → evaluate → save)

不满足时, 使用模块级函数 + `@dataclass` 传递只读配置, 禁止包装成类。

### 方法数量约束

- 每个类的方法数 (不含 `__init__` 与 dunder 方法) **不超过 5 个**
- 每个方法承担一个**完整阶段**, 不是单个步骤
- 禁止为每个小步骤写方法。阶段内部的顺序逻辑直接写在该方法体内, 用行注释分段
- 超过 5 个方法时, 必须说明理由, 或拆分职责到多个类

### 禁止的过度工程化

- 禁止抽象基类、`ABC`、`Protocol`, 除非项目内已有 ≥ 2 个真实实现
- 禁止 mixin、多重继承、元类
- 禁止 getter / setter, 直接使用属性
- 禁止为类配套创建 Factory 类、Builder 类、Registry 类
- 禁止把简单脚本包装成类
- 禁止只被调用一次的 `_private` 方法 — 内联回调用处 (与第 2 条一致)

### 类内组织示例

```python
@dataclass
class TrainConfig:
    model_name: str
    lr: float
    epochs: int
    batch_size: int


class Trainer:
    def __init__(self, cfg: TrainConfig) -> None:
        self.cfg = cfg
        self.model: nn.Module | None = None
        self.optimizer: Optimizer | None = None
        self.history: list[float] = []

    def train(self) -> None:
        # 初始化模型与优化器
        ...
        # 逐 epoch 训练, 记录 loss
        ...

    def evaluate(self) -> dict[str, float]:
        ...

    def save(self, path: Path) -> None:
        ...
```

三个方法, 每个对应一个完整阶段。阶段内部的步骤直接顺序写在方法体内, 不拆分为 `_build_model` / `_build_optimizer` / `_run_epoch`。

## 4. 过度工程化警戒

**本条的定位: 每当准备新增抽象时, 先读一遍本节, 确认自己没有触发以下信号。**

过度工程化比「代码不够优雅」危害更大。它增加的是认知负担、维护成本与出错面, 换来的往往是「未来可能有用」的想象。以下每一条都是**触发即停止**的信号, 命中时必须回退到最简单的实现。

### 抽象层信号

- **为单个实现创建接口**: 只有一个类会实现某个抽象时, 抽象层是纯粹的浪费。删掉接口, 直接用具体类
- **为「未来可能替换」预留扩展点**: 未来没有发生的事不要现在设计。替换时再重构, 成本远低于长期维护无用抽象的代价
- **三行代码的「通用化」**: 为了「以后可能复用」把一个明确操作泛化成带参数、带回调、带策略对象的函数。三行直白代码优于一个「灵活」的抽象
- **命名里带 `Manager`、`Handler`、`Processor`、`Service`、`Helper`、`Util`、`Base`**: 这些名字通常意味着职责不清。重新审视它是否真的需要存在

### 结构信号

- **文件数 > 功能数**: 一个功能拆到 5 个文件时, 说明抽象过度。合并
- **import 链超过 3 层**: `a` 导入 `b` 导入 `c` 导入 `d` 只为了用一个函数, 是分层过度的直接证据
- **为单一用途创建模块**: 一个模块只导出一个函数, 且该函数只被一处调用, 直接放到调用方
- **引入目录层级**: `utils/`、`core/`、`common/` 这类目录若无 5 个以上真实成员, 不要建立
- **配置对象嵌套**: `cfg.train.optimizer.lr` 超过两层的配置结构, 说明在设计一个「万能配置系统」, 停手

### 模式信号

- **单例、工厂、建造者、策略、观察者、访问者**: 除非项目内已有同模式的 3 个真实用例, 否则禁止引入
- **依赖注入容器**: 手工传参已足够, 引入容器是自找麻烦
- **插件系统、注册表、钩子机制**: 没有第三方扩展需求时, 这些都是负担
- **事件总线、消息队列**: 单进程单模块内的解耦不需要这些
- **泛型参数超过 2 个**: `Dict[str, List[Tuple[int, T]]]` 这类嵌套泛型说明数据结构设计有问题, 用 `@dataclass` 重构

### 代码信号

- **超过 3 个布尔参数**: `def f(a, b, c, flag1, flag2, flag3)` 是在用一个函数做三件事, 拆开
- **`**kwargs` 无类型约束的透传**: 掩盖真实签名, 让类型检查失效
- **为「可测试性」注入一切**: 连 `time.time`、`random.random` 都要注入时, 是在为测试写代码而不是为功能写代码
- **过度使用装饰器**: 一层装饰器是清晰的, 三层装饰器叠加时需要停下来问「这是在解决真问题吗」
- **自定义异常类体系**: 项目内异常类超过 5 个时, 大概率是在设计一套「企业级异常框架」

### 自我检查问题

提交任何新增抽象前, 必须能回答:

1. 现在有几处调用它? **少于 2 处 → 删除**
2. 如果删掉这层抽象, 最坏结果是什么? **如果只是「代码稍长」→ 删除**
3. 我是为了解决当下问题, 还是为了「以后可能」? **后者 → 删除**
4. 这个抽象能在一句话内解释清楚吗? **不能 → 重新设计或删除**

### 与第 2、3 条的关系

- 第 2 条管**小逻辑**: 不要抽函数
- 第 3 条管**大功能**: 用类但类要瘦
- 第 4 条管**中间地带**: 不要为了「看起来专业」而引入抽象层、设计模式、目录结构

三条合起来的核心原则: **能用 10 行顺序代码解决的, 不要用 3 个类 + 1 个接口 + 1 个工厂解决。**

## 5. 最大化复用

新增功能前, 必须按以下优先级选择实现方式:

1. **项目内已有函数 / 类 / 工具模块** — 先搜索确认, 禁止重复造轮子
2. **Python 标准库** — `itertools`、`functools`、`collections`、`pathlib` 等优先
3. **项目已声明的第三方依赖** — 检查 `pyproject.toml` / `requirements.txt`
4. **新增依赖** — 仅当前三者都无法满足, 且必须显式说明理由后等待确认

硬性要求:

- 禁止为单个功能引入新依赖
- 禁止复制粘贴已有实现后再局部修改, 应直接复用或重构原函数
- 禁止用 `pip install` 解决问题而不检查现有依赖
- 引入新库前, 先说明: 为什么现有方案不够用、新库的体积与维护成本、是否有更轻量的替代

## 6. 数值计算向量化

**禁止使用 `for` / `while` 循环逐元素执行数值计算。**

必须使用 NumPy / pandas / polars 等库的向量化 API。

```python
# 错误: 循环逐元素计算
result = []
for i in range(len(a)):
    result.append(a[i] + b[i])

# 正确: 向量化
result = a + b

# 错误: 循环累加
total = 0
for x in arr:
    total += x

# 正确: 内置聚合
total = arr.sum()
```

补充要求:

- **列表推导式 / 生成器表达式同样视为循环**, 禁止用于可向量化的数值计算。仅在数据非数值 (字符串、对象) 或规模极小且无向量化替代时使用
- 禁止用 `np.vectorize` 冒充向量化 — 它只是循环的语法糖, 无性能收益
- 优先使用库内置的聚合、广播、布尔索引、`np.where`、`np.select`
- 数据规模极小时 (元素数 < 10) 也不使用循环, 保持风格统一

例外情况 (允许循环):

- 存在跨迭代的状态依赖, 无法并行化 (如数值迭代收敛)
- 循环次数本身是算法的核心部分 (如牛顿法迭代)
- 数据本身是标量而非数组, 不要为了「向量化」硬把标量包装成数组

## 7. 类型标注全面

所有函数 (含 `__init__`、私有方法、嵌套函数) 必须标注参数与返回值类型, 使用符合 **Python 3.13** 的标注习惯。

- 使用新语法: `X | None` 而非 `Optional[X]`, `list[str]` / `dict[str, int]` 而非 `typing.List` / `typing.Dict`
- 业务数据结构必须使用 `@dataclass` 装饰器定义, 禁止用裸 `dict` 传递业务数据
- 禁止无理由的 `# type: ignore`。如确需使用, 必须在同一行注明原因:

  ```python
  value = lib_call()  # type: ignore[no-any-return]  # 上游库未提供类型存根
  ```

- **禁止孤立修改**: 修改任何函数签名 (参数、返回类型、默认值) 时, 必须同步更新所有调用点、docstring 及类型标注, 不得只改定义不改调用

```python
# 禁止
def process(data, cfg):
    ...

# 强制
def process(data: list[float], cfg: AppConfig) -> ProcessResult:
    ...
```

## 8. 禁止 try / except

**禁止在任何代码中使用 `try` / `except` / `try` / `finally` / `contextlib.suppress`。**

错误处理必须在编码设计阶段就解决, 而不是靠运行时兜底。异常捕获会让缺陷静默传播, 掩盖本应暴露的逻辑错误。

### 必须在编码前消除错误来源

写每一行可能失败的操作前, 先问: **这个操作在什么条件下会失败? 能否在调用前就排除该条件?**

| 场景 | 禁止写法 | 替代写法 |
|---|---|---|
| 字典取值 | `try: v = d[k] except KeyError` | `v = d.get(k)`, 或先 `if k in d:` |
| 类型转换 | `try: n = int(s) except ValueError` | `if s.lstrip("-").isdigit(): n = int(s)` |
| 除法 | `try: r = a / b except ZeroDivisionError` | `if b != 0: r = a / b` |
| 文件存在 | `try: f = open(p) except FileNotFoundError` | `if p.exists(): ...` |
| 属性访问 | `try: x = obj.attr except AttributeError` | `getattr(obj, "attr", default)` |
| 列表查找 | `try: i = lst.index(x) except ValueError` | `if x in lst: i = lst.index(x)` |
| 迭代取值 | `try: v = next(it) except StopIteration` | `v = next(it, default)` |
| 资源释放 | `try: ... finally: f.close()` | `with open(p) as f:` |
| JSON 解析 | `try: json.loads(s) except JSONDecodeError` | 使用返回 Result 的解析库, 或改为项目内已有校验函数 |
| 网络请求 | `try: r = get(url) except ConnectionError` | 使用项目内已有的请求封装, 由封装层统一处理失败语义 |

### 用类型系统表达「可能失败」

函数的失败可能性必须体现在签名里, 而不是藏在异常中:

```python
# 禁止: 失败通过异常隐式传递
def find_user(uid: int) -> User:
    ...

# 强制: 失败通过返回值显式表达
def find_user(uid: int) -> User | None:
    ...
```

调用方必须显式处理 `None` 分支, 编译器与类型检查器会强制这一点。

### 当确实无法避免时

某些第三方库的 API 设计强制以异常表达失败 (例如部分 C 扩展、旧版 SDK)。遇到这种情况:

1. **禁止自行添加 try / except**
2. **暂停并说明**: 哪个调用、为什么无法通过前置校验规避、有哪些候选方案
3. **等待确认后再继续**

是否引入异常捕获由人来决定, Agent 不得自行判断。

## 9. 资源与副作用管理

- 所有文件、网络连接、锁、会话对象必须使用 `with` 语句管理, 禁止手动 `.close()`
- 禁止在模块顶层执行有副作用的代码 (I/O、网络请求、环境读取、实例化服务)
- 禁止可变默认参数:

  ```python
  # 禁止
  def add_item(item, items=[]):
      items.append(item)
      return items

  # 强制
  def add_item(item: str, items: list[str] | None = None) -> list[str]:
      items = items if items is not None else []
      items.append(item)
      return items
  ```

- 禁止在函数内修改传入的可变参数 (列表、字典), 除非函数名明确表达该意图 (如 `sort_inplace`)

## 10. 禁止 print 调试

- 非 CLI 入口代码中禁止使用 `print()`
- 统一使用专门的日志库 (标准库 `logging` 或项目已有的日志封装), 禁止引入新的日志依赖
- 日志消息使用惰性格式化: `logger.info("x=%s", x)`, 禁止在日志中拼接 f-string
- 提交前必须清除所有临时调试输出

## 11. 字符串格式化

**一律使用 f-string。**

- 禁止 `%` 格式化 (日志例外, 见第 10 条)
- 禁止 `str.format()`
- 禁止用 `+` 拼接构造带变量的消息
- 需要格式化数字/日期时, 在 f-string 内使用格式规范: `f"{value:.2f}"`、`f"{date:%Y-%m-%d}"`

```python
# 禁止
msg = "用户 %s 登录失败, 重试 %d 次" % (name, count)
msg = "用户 {} 登录失败".format(name)
msg = "用户 " + name + " 登录失败"

# 强制
msg = f"用户 {name} 登录失败, 重试 {count} 次"
```

## 12. 真值判断与容器操作

- 真值判断禁止与 `True` / `False` / `None` 做 `==` 比较:
  - 用 `if flag:` 而非 `if flag == True:`
  - 用 `if x is None:` 而非 `if x == None:`
- 禁止 `if len(lst) > 0:`, 直接用 `if lst:`
- 频繁 `in` 查询的容器必须用 `set` 或 `dict`, 禁止用 `list`
- 循环内禁止字符串拼接, 改用列表收集后 `"".join()`

```python
# 禁止
result = ""
for item in items:
    result += str(item)

# 强制
result = "".join(str(item) for item in items)
```

## 13. 数据规模与性能直觉

写循环前先问: 数据规模量级是多少?

- 元素数可能 > 1000 时, 禁止 O(n²) 嵌套循环, 改用集合、字典索引或排序后双指针
- 循环内禁止重复计算不变量, 提取到循环外
- 优先选择库内置的高层 API (如 `collections.Counter`、`itertools.groupby`) 替代手写逻辑

---

## 14. 遵循 PEP 8

严格遵循 PEP 8, 关键条目:

- 缩进 4 空格, 禁止 Tab
- 行宽 ≤ 88 字符
- 命名: 模块/函数/变量 `snake_case`, 类 `PascalCase`, 常量 `UPPER_CASE`
- import 分组顺序: 标准库 → 第三方 → 本地模块, 组内按字母序, 禁止 `from x import *`
- 二元运算符两侧各一个空格, 逗号后一个空格
- 顶层函数/类之间空 2 行, 类内方法之间空 1 行
- 禁止行尾多余空格, 文件末尾保留单个换行

**可执行要求**: 提交前必须通过 `ruff check --select E,F,I,UP,B,C4,N,W` 和 `ruff format`, 格式问题不允许人工辩解。

## 冲突处理

若两条规则在当前任务中冲突, 优先级为:

**第 8 条 (禁止 try / except) > 第 7 条 (类型) > 第 4 条 (过度工程化警戒) > 第 3 条 (OOP 边界) > 第 2 条 (最小函数化) > 第 5 条 (复用) > 其余**

规则边界的判定顺序:

1. 先按第 4 条检查是否在引入不必要的抽象。命中任一信号 → 回退到最简实现
2. 再按第 3 条判断是否需要类。不满足三个条件 → 用模块级函数
3. 需要类时, 类内方法同样受第 2 条约束 — 一次性逻辑内联, 不得抽为方法
4. 第 2 条与第 4 条的关系: 第 2 条针对函数, 第 4 条针对抽象层、模式与结构。两者独立适用

任何无法同时满足的情况, 必须暂停说明, 不得自行取舍。
